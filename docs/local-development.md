# Local development

A full Postgres, Auth, Storage and Edge Function stack on your machine, with the fixture
data loaded. Once the images are pulled it runs with the network off.

## 1. One-time setup

```bash
brew install --cask docker      # or colima; anything that gives you a Docker daemon
open -a Docker                  # accept the licence once
npm ci
```

The Supabase CLI is a **devDependency** (`CI3`), not a global install, so CI and every
laptop run the identical version. There is nothing to install separately and nothing to
keep in sync — `npx supabase` resolves to the pinned one.

## 2. Every day

```bash
npm run dev:db          # supabase start  — first run pulls ~1.5 GB of images
npm run db:reset        # replay every migration from 0001, then load supabase/seed.sql
npm run db:status       # the local URLs, anon key and service-role key
npm run dev:db:stop     # supabase stop
```

`db:reset` is the one to reach for whenever anything looks wrong. It is cheap, it is
destructive only to local data, and replaying from `0001` is the thing that proves the
migration set is coherent — a gap or a bad dependency order fails here rather than
against staging.

## 3. What you get

| Service | URL |
|---|---|
| API | `http://127.0.0.1:54321` |
| Postgres | `postgresql://postgres:postgres@127.0.0.1:54322/postgres` |
| Studio | `http://127.0.0.1:54323` |
| Inbucket (all outbound mail) | `http://127.0.0.1:54324` |

Local mail is captured by Inbucket and never leaves the machine — which is what makes the
email-OTP sign-in flow testable offline, and v1's auth is Google, Apple and email OTP with
no passwords (decision `U1`).

## 4. Secrets

**Local needs none.** The CLI prints a fixed anon key and service-role key for the local
stack, and Razorpay is stubbed offline (`docs/testing-strategy.md` §5.1), so `local` runs
without a Razorpay account at all.

If you do set anything, the `rzp_test_` prefix rule still applies and will refuse a live key
on a laptop exactly as it would in CI (`docs/environments.md` §2).

## 5. Running the tests

```bash
npm run smoke      # typecheck, lint, migration rules, unit tests — ~6s, no Docker needed
npm run test:db    # db reset + the pgTAP suites — needs the stack up
npm run test:all   # both
```

`npm run smoke` is the only one CI runs on every push. `test:db` needs Docker because the
pgTAP authorization suite cannot run against a bare Postgres: `app_user.id` is a foreign key
to `auth.users(id)` and impersonation reads `auth.uid()` from `request.jwt.claims`, so the
GoTrue auth schema has to be real (`docs/testing-strategy.md` §6).

To close it: install a Docker daemon, run §2, then `npm run test:all`.

## 7. If something breaks

- **`supabase start` hangs or errors** — `npm run dev:db:stop`, then `docker ps` to check
  nothing is holding ports 54321-54324.
- **A migration fails on reset** — read it top to bottom; `db reset` replays from `0001`, so
  the failure is in the first migration that is wrong, not necessarily the newest.
- **`node` or `npm` dies with a dyld error about `libicui18n`** — a Homebrew install upgraded
  `icu4c` out from under the Node binary. `docs/learnings.md`, 2026-08-07 has the fix.
