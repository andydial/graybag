# Decisions — Auth

`U1`–`U5` · part of the decision log. Index: `docs/decisions.md`. Superseded entries and build-log history: `docs/decisions-archive.md` (never authoritative).

**Decision IDs are permanent and never move between files.** If you change a decision here, change it in the same PR as the code — never silently diverge.

| # | Decision | Why |
|---|---|---|
| U1 | **Google / Apple / email-OTP sign-in — no phone OTP, no passwords.** *Supersedes the original "Phone + OTP" decision.* Google Sign-In is primary; Sign in with Apple on iOS (Apple requires it once Google is offered); email OTP via Supabase `signInWithOtp` for non-Google addresses. Phone OTP becomes a fast-follow *addition*, not a replacement. Mobile number stays a **profile field** (kitchen contact + last-4 search), never a login credential. Back-office unchanged (email). | DLT SMS registration had weeks of lead time on the launch critical path — Google/Apple/email have none. Cheaper (no ~Rs 0.15/OTP, no SMS account). Lower friction for an Android-heavy audience already signed into Google. Removes an account-takeover migration risk: the legacy `mobile` field is a *number* type that already lost leading zeros and `+91`, whereas Bubble exports email, so `E03-16` matches on email unambiguously. Email infra (SPF/DKIM/DMARC) is already required for GST invoices (`E07-05`), so the work is shared, not extra. DLT registration (`E00-06`…`E00-09`) continues *off* the critical path for future order-update SMS. |
| U2 | **No password migration** | Bubble cannot export password hashes — a hard limitation. Everyone re-authenticates once regardless, so switching to OTP costs nothing extra. |
| U3 | Long-lived refresh tokens (90–180 days) with silent refresh | Returning users rarely re-authenticate, keeping friction (and, for email OTP, message volume) low. Android SMS Retriever now rides with the phone-OTP fast-follow (`U1`), not v1. |
| U4 | **Sender identity for all transactional mail** (OTP, confirmations, invoices) | From `GrayBag <orders@graybag.com>`; Reply-To `support@graybag.com` (parents reply — it must reach a human); no `no-reply@` addresses. Exactly **one** SPF record on the domain — extend the existing Google Workspace record, never add a second (two SPF records fail silently and are the commonest cause of spam-foldering). DMARC starts `p=none`, tighten to `p=quarantine` after two weeks of reports. Shared infra with `E07-05`. |
| U5 | **A signed-out user reads the menu through literal table grants plus RLS policies** — `[AUTH-01]`, migration `0012`. `anon` holds SELECT on twelve menu tables and one `security_invoker` view; a policy on each decides which rows. **Supersedes the `SECURITY DEFINER` functions `0010` shipped**, which are dropped. | `AR7` requires the app be browsable before anyone identifies themselves; the privilege baseline (`PB1`, `[AZ-03]`) gave `anon` nothing at all. Andy chose table grants and, on review, held to it. The argument that settled it: **`E02-26`, found in the same migration, was a `SECURITY DEFINER` function about a child reachable by `anon`** — so adopting that pattern for the product's most-called read put it behind the mechanism that had just failed. A definer function carries its own authority and its body is the boundary; a grant plus a policy carries the caller's, and the database is the boundary. Four assertions in the authorization suite were rewritten rather than routed around, and they are stronger: the old ones asserted *structure* ("anon holds no table privilege"), which a grant with no policy satisfies for the wrong reason; the new ones assert *behaviour* as the role — anon reads a published dish and gets it, retires the menu and gets nothing, reads a child and gets nothing. `public_menu` is a `security_invoker` view carrying no authority of its own, and exists only to collapse four dependent round trips into one on the app's hottest path (CLAUDE.md: network is the constraint). Accepted cost, unchanged from `0010`: **the menu, including prices, is readable by anyone holding the anon key**, which ships in the app. |
| U6 | **The back-office session lives in `localStorage`, bounded by two windows: a sliding **30 days** since the last session write, and an absolute **90 days** from the original sign-in that nothing extends.** *Reverses the `sessionStorage` choice made when `E12-06` was built.* Either window ending ends the session. Both are evaluated on every storage access, not once at page load. | Andy, 2026-09-08: kitchen and admin staff were re-doing the email-and-OTP dance constantly, *"including at 3 AM"*. The original `sessionStorage` reasoning was sound — a kitchen tablet is shared and never locked, so a session left behind can read every child's name — and its cost only became visible in daily use: `sessionStorage` is scoped to the **tab**, so closing it, rebooting the tablet, or opening the board in a second window destroyed the session. It was never token expiry; `persistSession`/`autoRefreshToken` have been on since `E03-20`. **Nothing server-side would ever end this session** — `sessions_timebox` and `sessions_inactivity_timeout` are both `0` on production and staging — so these two constants are the only bound that exists. **This shipped first as a single fixed 30-day window measured from sign-in and never re-stamped**, on the argument that a sliding window "would never be reached by anyone still using the tool, which is the one population it is for". Andy corrected it the same day: *"Make the 30 days slide… so a device in regular use never sees an OTP. Keep the absolute cap sensible — 90 days from original sign-in — so an abandoned device does eventually expire."* The original objection was right about the mechanism and wrong about the goal — a device in regular use never seeing an OTP is the **point**, not a hole — and what it was really describing is a session with no ceiling, which the 90-day cap supplies. Two windows gets both properties; one was a false economy. The residual risk is accepted and stated: on a shared tablet a signed-in session waits for the next person until somebody signs out. `MEMORY_ONLY` (`kitchen/types.ts`) is untouched, so what persists is a session and not a child's name. See `U7`, the condition that makes this acceptable, and `U9`, the hole the sliding window opened. |
| U7 | **Sign out is a permanent element of `BackofficeShell`, mounted before the grant read and outside its `try`.** | It had silently ceased to exist. `E10-43` put it in `BackofficeNav`; `E10-55` replaced that component with the shell and did not carry the button across, so from that merge until `E12-42` **no back-office page had any way to sign out**. Nobody noticed because the session died with the tab, which made closing the tab the sign-out — an accident that `U6` removes, which is why the two ship together rather than in sequence. It is outside the `try` because a failed `fetchMyAccess` deliberately leaves the rail empty (`E10-73`): mounting sign-out inside it would make the one failure that strands somebody on a bare frame also the one that removes their way out of it. `signOut()` purges local storage in a `finally`, so a failed server call still ends the session locally — a sign-out that reports an error and leaves a usable refresh token on a shared tablet is the worst available outcome. |
| U8 | **`/signin` remembers the last address in `localStorage` and prefills it. The address and nothing else — never a token, code or user id.** Written **after** the code is accepted, not when it is sent. Survives sign-out and session expiry. | Andy, 2026-09-08. Back-office accounts are shared organisational addresses nobody has committed to memory, and the OTP dance began with retyping one; the browser's own `autocomplete="email"` offers the *person's* saved addresses, which on a kitchen tablet is often nobody's. Written after acceptance so a typo — or a colleague's address typed once — never becomes the prefill. A six-digit code in `localStorage` would turn "I have this device" into "I have this account" and defeat the point of sending the second factor somewhere else, so `rememberEmail` refuses anything that is not an email address and is the only writer of the key. It survives sign-out because it is a convenience and not a credential; clearing it would mean the person who signs out is the one person who has to retype. |
| U9 | **Expiry is latched in memory for the life of the tab, and only a successful OTP verification clears it.** The latch is opened *before* the code is exchanged and the stamps are written *after* it succeeds. | A sliding window opens a hole a fixed one did not. Purging expired keys is not enough: the Supabase client running in that tab still holds the session **in memory**, and its next silent refresh writes it straight back. Under the old fixed stamp that was survivable — the re-stamp produced a value still measured from nothing. Under a sliding window it is a resurrection, because the write sets `last-seen-at` to now and a session that had just expired is good for another thirty days with nobody having authenticated. Hence the latch: once a window closes, reads return nothing and writes are refused whatever the client does next. **The two halves sit at different points for a reason found while writing it.** Putting both after the exchange does not work: Supabase persists the new session *during* `verifyEmailOtp`, so a latch still closed at that moment sends the freshly minted token to the in-memory fallback — the person signs in, reaches the board, and is signed out again by their first reload. Opening the latch early resurrects nothing, because it only ever closes alongside a `purgeSession`, and on the common path (a page loaded after the window shut) there is no in-memory client left to write anything back. The stamps stay after success so a wrong code at `/signin` cannot extend a live session. |
