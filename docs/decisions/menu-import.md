# Decisions — Menu import

`MI1`–`MI6` · part of the decision log. Index: `docs/decisions.md`. Superseded entries and build-log history: `docs/decisions-archive.md` (never authoritative).

**Decision IDs are permanent and never move between files.** If you change a decision here, change it in the same PR as the code — never silently diverge.

Made in Q08 while building `tools/menu-import/`, the prototype that proves the spreadsheet
format before `E04-04` is built. The source workbook is **not in the repository** (`[MI-01]`),
so everything below is a choice about how the importer behaves, not a claim about the data.

| # | Decision | Why |
|---|---|---|
| MI1 | **A blank `Allergens` cell means *unknown*, never *none*.** `allergens_declared_none` is true only when the cell says so explicitly; a blank cell imports with no tags **and a warning** | These are the same JSON — an empty tag list — and they are opposite facts. A kitchen that has not filled the cell in has told us nothing, and rendering that as "no allergens" at add-to-cart is precisely the failure `D7` exists to prevent. Making the distinction a stored field rather than an inference is what stops it being lost the first time someone writes `if (!dish.allergens.length)` |
| MI2 | **What fails a row versus what merely warns is decided by whether being wrong could hurt someone**, not by how confident the parser is | Unparseable calories become `null` with a warning, because a missing calorie count harms nobody and a *guessed* one is worse than none. An unrecognised allergen fails the row outright. So does anything about money. The rule is written down because the natural instinct when an import strands 30 rows is to relax whichever check is loudest, and it must be obvious which checks are not available for relaxing |
| MI3 | **Every row below the header is accounted for: a dish, a rejection, or a counted blank.** `accepted + rejected + skipped == rows_below_header` is asserted by a test | A menu importer that quietly drops the four rows it did not understand produces a menu that is *almost* right, which is the hardest kind of wrong to notice. Unrecognised *columns* are reported for the same reason. Follows the same instinct as `D17` — the resting state must be loud |
| MI4 | **Zero dependencies. `.xlsx` reading is ~300 lines of `node:zlib` in `src/zip.mjs` and `src/xlsx.mjs`** | The repo has no `node_modules` and no lockfile, and this has to run for a non-developer with `node` and nothing else. Cost accepted: no ZIP64, no `.xls`, no `.csv`, and **no styles — so date cells are not interpreted**. No column in this format is a date; that is the first thing to fix if one is ever added. It throws a clear message on each rather than misreading |
| MI5 | **The importer never decides anything the data model has left open.** `food_type` is `null` on every dish (`[DM-17]`) and `price_is_tax_inclusive` is `null` on every dish (`[DM-20]`), both emitted explicitly rather than omitted | An importer is the most tempting place in the system to quietly settle an open question, because it is the only place that has to produce a value for every field. Writing the null explicitly, and emitting a file-level notice on every run, means the gap stays visible instead of being answered by whatever the first consumer defaults to |
| MI6 | **The allergen synonym table carries kitchen vocabulary, not textbook vocabulary** — `paneer`, `maida`, `til`, `kaju`, `sarson`, `atta`, `dahi` | The people who write the Allergens column write what they cook with. A table that only knows "milk" and "wheat" pushes every real cell into the unmapped bucket, and a validator that fails everything gets switched off |

## Added by `E04-01`, 2026-08-09 — the column `MI1` needed and did not have

| # | Decision | Why |
|---|---|---|
| MI7 | **`dish.allergens_declared_none` is a stored column (`0006`), defaulting to `false`, and the three allergen states are read from it plus the `dish_allergen` rows** — rows present = declared; no rows + `true` = declared none; no rows + `false` = **unknown** | `MI1` says a blank `Allergens` cell means *unknown*, never *none*, and the importer implements that faithfully — it emits `allergens_declared_none` per dish and the run report counts the cells that said so explicitly. **`dish` had nowhere to put it**, so the importer computed the distinction and the load discarded it, leaving only "has tags" and "has no tags". Those are the two states `MI1` exists to keep apart, and downstream the consequence is not cosmetic: `D7` keeps structured tags so the add-to-cart warning (`E05-05`) is nearly free, that warning reads the tags, and a dish nobody has described would have rendered as allergen-free. On data about children, where non-negotiable #4 applies. `false` is the right default for every existing row because nothing already loaded came from a cell that said "none" — the safe reading is the resting state, the same instinct as `D17` and `C6`. `mayStateNoAllergens()` exists so the plausible one-line wrong version (`if (!allergens.length)`) has something to be replaced by, and `allergenWarning()` returns `warn: true, reason: 'unknown'` for an undescribed dish **even when the recipient has no recorded allergies** |

## Added by `E04-04` / `E04-05`, 2026-08-09 — validate, preview, apply

| # | Decision | Why |
|---|---|---|
| MI8 | **The importer produces a *plan*, and applying it is a separate act. The plan carries a SHA-256 of the workbook it was built from, and apply refuses if the file has changed since** | "Never silently overwrite" is not satisfied by asking for confirmation — it is satisfied when the operator has seen every field-level change before any of them happen. The failure this closes is specific and quiet: preview a diff, somebody re-exports the sheet over the same filename, apply writes changes nobody read. Fingerprinting content rather than path or mtime is what makes "the plan you approved is not the change this file would make" a refusal instead of a coincidence |
| MI9 | **A dish absent from the sheet is reported but NOT deactivated, unless `--deactivate-missing` is passed** | The ordinary case is a kitchen sending the ten dishes that changed, not a full re-export. Treating absence as deletion turns the ordinary case into an emptied menu, discovered at lunchtime. Absence is always *reported*, because "the sheet does not mention these" is the single most useful signal that the wrong file was exported — it is acting on it that is opt-in |
| MI10 | **Two blockers refuse an apply outright: deactivating more than 25% of a live menu, and a plan that would change nothing at all.** Overriding is `--force`, and the override is recorded in the receipt | Neither is a validation error — the plan is internally fine. Both are the shapes that mean *the operator imported the wrong file*, and both are cheap to wave through and expensive to discover afterwards. "No changes" and "I read the wrong tab" are indistinguishable from outside, and only one of them is harmless. Recording the override matters because the question after a bad import is always "did somebody force this?", and an override that leaves no trace cannot answer it |
| MI11 | **Deactivations run last, and one failed row does not abandon the rest** | The two failure modes of a half-finished apply are not symmetric. Stopping early with creates done and deactivations pending leaves a menu with too many dishes — an operator can spot a stale item. The reverse leaves too few, and nobody notices an absence until the orders do not arrive. Continuing past a failure means the receipt is a to-do list rather than a mystery; stopping at the first error leaves a menu that is neither the old one nor the new one, with no record of which rows still need doing |
| MI12 | **The write path takes an injected executor, so every rule above is tested without a database** | A write path exercised only against a live Postgres is a write path whose failure modes are exercised never — and the rules that matter here (ordering, partial failure, forced overrides) only show themselves when something goes wrong. The executor deliberately has no `deleteDish`: absence deactivates, and a delete method would be one refactor away from being called |
| MI13 | **The plan report prints allergen changes first, then prices, then everything else** | The ordering is the control, not decoration. `MI2` decides what fails versus warns by asking whether being wrong could hurt someone, and the same question decides what an operator scanning a 50-row diff must not be able to miss. Safety below forty price rows is the same as not printing it. Prices render in rupees because `Rs 6500` and `6500` are different numbers and an approver should not have to divide by 100 |
