# Analytics

The contract itself is `docs/posthog.md`; this is the record of the judgement calls behind it.
`E15-17` and `E15-20` established the allowlist and the fetch client; `E15-24` is where the funnel
was first read against real parent behaviour and found to be measuring the wrong things.

| # | Decision | Why |
|---|---|---|
| AN1 | **`distinct_id` is always present. Events sent before sign-in carry an `anon-…` id, and `identify` emits a `$identify` with `$anon_distinct_id` to merge them onto the parent — but only when something actually went out anonymously.** | It used to be omitted entirely while nobody was identified, and PostHog's capture API requires it, so **every signed-out event was discarded at the far end for thirty days**. It presented as arithmetic that could not be true: `signin_started` 2 against `signin_completed` 30, `cart_started` 3 against `add_to_cart_tapped` 28 — one defect, both symptoms, and both on events that fire before the gate (`signin_started` by definition, `cart_started` because `AR7` has the cart filling signed out). The fingerprint was visible in the project all along: `distinct_ids` equalled `persons` for every event, so not one anonymous event had ever arrived. Fixing `distinct_id` alone would only have moved the problem — the events would land on a separate anonymous person and still be absent from the parent's funnel — which is why the merge is half of this decision rather than a refinement of it. It is conditional because aliasing an id PostHog has never seen is a wasted round trip on a school-gate connection. **The anon id lasts one launch**, because persisting it needs storage and this module ships over the air with no native module; a parent browsing signed out across two launches is two anonymous people until they sign in. `reset()` on sign-out is the other half: a handset is shared, and the previous parent's id used to persist for the life of the process — which is also the mechanism behind the only two `signin_started` events that ever landed. |
| AN2 | **A closed vocabulary is per-event where a key means different things — `EVENT_ENUM_VALUES` overrides `ENUM_VALUES`.** | `reason` was global because one event used it. Three do now and they answer different questions: why a parent turned back (`payment_abandoned`), why the order could not be attempted (`order_blocked`), and who refused it (`payment_failed`). Unioning the lists would have made every value legal on every event — `order_blocked` could have reported `dismissed` — and a vocabulary that accepts anything has stopped being a check. The per-event map is consulted first and falls back to the global one, so an event without an entry behaves exactly as before. |
| AN3 | **`order_value_inr` is whole rupees, and this is the one place money stops being integer paise.** | Non-negotiable #3 protects **arithmetic**: nothing that computes a price, a tax component or a ledger entry may see a float, and none of them call `rupeesFromPaise`. A funnel reporting revenue in paise is a funnel nobody reads. It returns an **integer** rather than a float so the value cannot be mistaken for a precise amount or accumulate representation error when a column of them is summed. The cost is stated rather than hidden: **a PostHog revenue total will disagree with the ledger by up to fifty paise per order, by construction.** The ledger is the authority; PostHog answers "roughly what is an order worth, and which schools", which is a different question. |
| AN4 | **`school_id` may travel; `school_class_id` may not. Counts of children may travel; a child's identity may not.** | The line is worth stating precisely because it is close. A school is an **institution** — `0002`'s own comment already records that class labels and break times are not personal data — and which school an order is for is an attribute of the *order*. Which **class** a child is in is an attribute of the child, and `school_class_id` stays in `FORBIDDEN_KEYS` along with `recipient_id`; `school_id` + `recipient_id` would be a child's school, which is why the second never leaves. `child_count` is permitted for the same reason and is the only declared property whose name contains a regulated word, so it is pinned by value in the test that scans for them. DPDP **s.9(3)** is the line: the Data Principal is the parent, an adult, and the moment an event carries a child's attribute, parent-analytics becomes behavioural monitoring of a child and no consent cures it. |
| AN5 | **`checkout_started` is the funnel's denominator, not `place_order_tapped`.** | Read from the live data rather than reasoned about: `place_order_tapped` fires **three and four times in a row** as a parent presses a button that does not visibly respond, and `payment_started` reached attempt 4 inside one second. A tap is a gesture and gestures repeat under frustration; `checkout_started` fires once, where `create_checkout` is actually called, including on a retry that reuses the order group. The duplicate taps are a real defect in their own right and are filed as `E15-25` rather than fixed here, because the week a school goes live is the wrong week to change the ordering path. |
| AN6 | **`signup_started` is an acknowledged over-count; `signup_completed` is exact.** | `U1` makes account creation implicit — one `signInWithOtp` both creates and resumes — so at the moment the sign-in screen opens **nothing knows whether the address is new, and it must not**: the "if that address has an account" copy exists precisely so the screen is not an account directory, and telling the funnel would mean telling the client. `signup_completed` is authoritative, from `AuthUser.isNewAccount`, which compares the provider's own `created_at` and `last_sign_in_at` rather than the device clock (a wrong clock would otherwise mislabel everybody). Its 30-minute window against a 60-minute OTP means a parent who verifies slowly is counted as *returning* — under-counting signups, which is the safe direction, because inventing new families makes acquisition look better than it is. `signup_started` uses "this install holds no session", which is also true of a reinstall. Read the pair as a ceiling and an actual, never as a ratio. `app_opened`/`is_first_open` would be the honest signal; it is declared in the allowlist with **no emitter anywhere** and needs a persisted first-run flag, which needs storage an OTA cannot add. |
| AN7 | **A dashboard property must never be able to slow or fail a payment.** `is_first_order` is read on cart **mount**, and the break-window style `.catch` is the pattern for all of them. | It needs `fetchOrders`, and the obvious place to put it is where the event fires — inside the payment path, the week a school goes live. A property nobody has ever had is not worth one added failure mode on checkout. The cart is a screen a parent sits on choosing a day, a break and a quantity, so there is time for one light read long before they commit; on failure it stays `null` and the property is **omitted** rather than reported as `false`, which would claim every order was a repeat. Same reasoning as `E09-42`'s break-window read on the kitchen board: the nicety is allowed to fail, the job is not. |
