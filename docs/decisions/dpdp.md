# Decisions — Consent, retention and DPDP

`C1`–`C20` · part of the decision log. Index: `docs/decisions.md`. Superseded entries and build-log history: `docs/decisions-archive.md` (never authoritative).

**Decision IDs are permanent and never move between files.** If you change a decision here, change it in the same PR as the code — never silently diverge.

Made in Q10 while writing `docs/dpdp-compliance.md`. **Everything about the *law* in that
document is provisional on `E20-01`, which has not been done.** What follows is not law — it is
a set of choices about the **machinery** that records and enforces whatever the lawyer says, and
each one is decidable now precisely because it does not depend on the answer. §0 of that
document draws the line between the two.

| # | Decision | Why |
|---|---|---|
| C1 | **Consent is written in the same transaction as the data it authorises — at *both* ends.** Adding a dependent writes the `recipient`, the `guardian_link` and the `consent_record` rows atomically; **removing one writes the `withdrawn` rows in the transaction that sets `deleted_at`** | The first half was already in the schema. The second half is the one that gets missed, and it is not optional: `auth_can_manage_recipient()` requires `recipient.deleted_at is null`, so once a dependent is soft-deleted **nobody can write a consent row about them ever again**. Deferring the withdrawal to a job or a later request means `current_consent` reads `granted` in perpetuity for a child who was removed a year ago — the exact opposite of what the record exists to prove. `E20-16` |
| C2 | **A `consent_purpose` row's meaning is immutable. A purpose that changes — new recipient, new use — is a *new* purpose, and the old consent is marked `superseded`** | Editing the meaning in place silently converts every historical `granted` row into evidence of consent to something the person was never shown. The row is cheap; the re-ask is the entire point of purpose-scoping. A privacy-notice update on its own does **not** invalidate consent — only a change of purpose does |
| C3 | **Withdrawal is a new row, never an update, and application code reads consent only through the `current_consent` view** | The question a regulator asks is "was there consent *on the 14th*", which a flag cannot answer and an event log answers trivially. The view half matters as much: it is `security_invoker`, so it inherits RLS, and hand-rolled "latest row" logic in application code both drifts and escapes the policy |
| C4 | **Policy acceptance and purpose consent are two different gates and are never conflated.** `user_policy_acceptance` is the contract gate (`blocks_ordering`); `consent_record` is the per-purpose processing gate | The two tables look redundant, which is what makes this the most likely mistake in the whole area. Treating "I agree to the Privacy Policy" as authority to store a child's health data is the blanket consent that purpose-scoping exists to stop, and it is one line of code away at all times |
| C5 | **`allergen_health_data` is separately consented and declining it is a supported end state**: no warning, not no service. Withdrawing it deletes every `recipient_allergen` row and `recipient.allergy_note` outright, in the same transaction | It is health data about a minor — the most sensitive thing in the system — so bundling it with the required purposes would make the required consent conditional on giving up something optional, which is the definition of consent that is not free. The deletion is outright rather than anonymised because, unlike an invoice, nothing statutory retains a child's allergy list |
| C6 | **Retention is data, and a personal-data table with no `retention_policy` row is an *alert*, not "keep forever"** | Same instinct as `D17` (RLS enabled with no policies, so the resting state is "nobody can read anything") and `MI3` (every row accounted for). A retention schedule that silently omits a table is indistinguishable from one that covers it until a regulator asks. The purge job therefore asserts coverage and dry-runs before it deletes, with a volume tripwire — a purge that suddenly wants 100× the usual rows is a cutoff-arithmetic bug, and it is unrecoverable once it has run. `E20-19` |
| C7 | **The breach clock starts at the first credible signal, not at confirmation** | The timestamp we will be asked for is when we became *aware*, not when we finished investigating, and the earliest applicable deadline may be six hours (`CERT-In`, §8.4). Waiting for certainty turns a 72-hour obligation into a 20-hour one, and the cost of a false start is one wasted afternoon. Corollary written into the runbook: containment comes first but **evidence preservation is part of containment** — no log deletion, no "cleaning up" |
| C8 | **Every data-subject request becomes a `data_subject_request` row at intake, from every channel — app, email, web form, a phone call taken by Andy** | `ix_data_subject_request_due` is the only thing that makes an approaching statutory deadline visible, and a request that lives in an inbox is invisible to it. Missing a deadline fails silently by construction — nothing errors when a date passes — so it also needs its own alarm (`E20-17`), same reasoning as `PY3` |
| C9 | **The consent record survives erasure**, and its own retention runs from the erasure date rather than from the account's | It is the evidence that holding the data was lawful. Deleting it as part of "delete everything about me" destroys our own defence for the period we *were* entitled to process, and leaves the invoice — which is retained by statute — standing with no recorded basis behind it |

### `[DM-12]` — consent is captured at child creation, and verification is one swappable step — 2026-08-10 (Andy)

| # | Decision | Why |
|---|---|---|
| C10 | **`[DM-12]` was one question being read as two, and separating them is what makes it buildable now.** *Recording* consent — what, when, by whom, against which version of the notice — is required by every answer `E20-01` could give, and was never blocked on a lawyer. *Verifying that the consenting adult is really the parent* is the legal question, and its three plausible answers differ enormously in build cost | The column comment on `consent_record.verification_method` said "DO NOT BUILD THE CONSENT UI UNTIL `E20-01` RETURNS", and taken literally it blocked `E05-01`, which blocked `E05-16`, which is why no real user could place an order at all. The record's shape does not depend on the bar; only the bar depends on the bar |
| C11 | **`parental_verification_method()` is the only thing in the system that decides the bar**, and v1 returns `authenticated_account_holder` | This is what makes `E20-01` a one-function change instead of a rebuild. The v1 answer is a real check rather than a placeholder — the session is established by Google, Apple or an email OTP (`U1`), so the person ticking the box has demonstrated control of the account — and it is deliberately the weakest of the three plausible bars, which is a thing to say out loud rather than discover later. `verification_method` stays untyped `text` for the same reason it always was: it has to be able to record whichever answer comes back |
| C12 | **Two purposes, not one: `child_meal_service` (required) and `child_allergen_info` (optional).** Supplying allergy details without the second consent is **refused**, not silently dropped | `C5` in shape, enforced in `create_recipient`. Refusing is the whole point: a parent who typed "peanut allergy", had it quietly discarded, and believed the kitchen knew is the failure mode that matters here. A single blanket "I agree" is what the Act exists to stop, and making the health-data purpose required would make the required consent conditional on giving up something optional |
| C13 | **The notice shipped in `0015` is written for a parent and is NOT lawyer-approved.** It is version `1`; `E20-12` publishes the approved wording as version `2` | `content_sha256` and `policy_version_id` are what make this safe rather than sloppy: a consent given today records the exact wording that was on the screen, and a later approved version does not retroactively change what anybody agreed to. **It does mean production must not collect consent against version `1`** — see `[DP-10]`. Staging is fine and is where `E05-01` gets exercised |
| C14 | **`[DP-10]` resolved 2026-08-10 (Andy): nothing gates `0015` out of production, because production has no users and will not open before `E20-01` returns.** The premise is a commitment, not an observation — Andy tells us if it changes rather than us finding out | The alternative was building a per-environment migration gate, which does not exist and would be new machinery standing between every future migration and production, to protect against a state that cannot currently occur. The cheap lever stays documented instead: set `published_at` to null on version `1` in production and `create_recipient` refuses with `no_notice_published` until approved wording lands, which is one `update` and a **tested** refusal path rather than a mechanism. This is the shape to reach for whenever a risk is real but its precondition is under our control — write the lever down, test it, and do not build the machine |
| C15 | **GrayBag is NOT a child-directed service.** Its users are adults: parents paying for their children, and adults ordering for themselves. This is the answer to Apple's "Made for Kids" question and Google Play's Target Audience / Families questionnaire, and it is final (Andy, 2026-08-11) | The distinction is between *whose data we hold* and *who the product is for*. We hold data about children, which is why `E20` exists at all — but no child installs the app, signs in, browses or pays, and there is no child-facing surface to design for. Answering "yes" would pull GrayBag into Play's Families policy and Apple's Kids Category, both of which impose ad-SDK, content and review requirements aimed at products children use directly, and neither of which describes this one. Answering "no" does **not** weaken any DPDP obligation: those attach to processing a child's personal data regardless of who the user is, and `C1`–`C14` are unchanged. **Closed — do not re-raise unless the lawyer changes it.** |
| C16 | **No analytics, telemetry or behavioural tracking may ever touch a child's record**, asserted by `apps/mobile/src/architecture/child-data-telemetry.test.ts`, which fails the build (Andy, 2026-08-11) | The rule already existed in seven doc comments and in non-negotiable #4, and prose is not enforcement — `setMenuCache` was named in four comments during the whole period nothing called it. `E15` adds the first real telemetry sink this repo has ever had; at that moment the only thing between a child's first name and a third-party vendor would have been whoever wrote the line remembering seven comments in six other files. The guard scans the **argument span** of every sink call for tier-P/S fields in both spellings, strips comments first, and proves itself on fixtures **and** on a violation injected into a real file — because a guard whose only evidence is "the tree passes" would pass with its pattern list empty. Its blind spot is stated in the file: a child value assigned to an innocuously-named variable first. Adding a sink to the list is a visible diff; `E15` adds its vendor in the same commit that introduces it |
| C17 | **The published policy is the lawyer's baseline plus a tracked change log, and the grievance officer is Vivek, `vivek@graybag.com`** (Andy, 2026-08-11) | The lawyer-drafted privacy and refund policies are held **verbatim** in `docs/legal/*-baseline.md` and are never edited; `docs/{privacy-policy,refund-policy}.md` are notice **version 2** — the baseline body plus a change log naming every alteration and its reason. That split is the point: one file records what a lawyer approved, the other records what we changed after, and neither can be mistaken for the other. Three changes: under-13 → **under-18** (DPDP defines a child as under 18; 13 is COPPA, which is US law), a named **Grievance Officer** (the Act requires a published named contact, which a general `info@` alias is not), and retention **split in two** — financial records 7 years under GST and the Companies Act, a child's name/class/section/allergy details deleted on request or when the guardian link ends. One number could not honestly serve both, and folding a child's details into a tax retention floor is the opposite of data minimisation. The grievance address is separate from `SUPPORT_EMAIL` in code so a data complaint cannot land in the order-query inbox and miss a statutory clock. The `E20-24` template drafts are superseded, not deleted — parked in `docs/legal/superseded/` with a banner, because their DPDP detail is reference material for the next revision |
| C18 | **No published document states a retention period as a number until `E00-10` confirms it.** The privacy policy says financial records are kept "for as long as Indian tax and company law requires"; the figure of seven years is withdrawn (Andy, 2026-08-11, who supplied it) | It was never verified, and it may be **below** the floor rather than a safe over-estimate: the Companies Act 2013 appears to require books of account for eight years, and the GST record period runs 72 months from the annual return, on a different clock. **A published commitment shorter than the law requires is worse than vagueness** — vagueness is accurate, and a short number is a promise we would have to break to stay lawful. The correction is in the policy's own change log as row 3a rather than as a silent edit, because a tracked change log that quietly loses a claim is not tracking anything. **What this decision generalises to:** the number that was wrong appeared in five places within three days of being invented — the published policy, the generated in-app copy, a mobile test *asserting* it, and two migration/test comments — so the rule is that a period is stated **once**, in the document that publishes it, and everything else defers to that document rather than restating it. `C6` already says retention is data; this says the same about the prose |
| C19 | **`self_data_notice` says order history is kept for 24 months and the privacy policy says financial records are kept for as long as the law requires. Both are published, and they describe the same rows** | Found 2026-08-11 while correcting `C18`. `0022`'s notice body — which is a `policy_version` with `requires_acceptance`, so it is consented to rather than merely displayed — commits to **24 months** for order history; the privacy policy holds invoices, ledger entries **and order history** to a statutory floor that is certainly longer. One of the two is a promise we cannot keep. **Not resolved unilaterally**: changing a published notice body means a new `policy_version`, and `requires_acceptance` re-prompts everyone who has accepted the old one. Today that is nobody, which makes now the cheapest moment it will ever be — and after ~150 Amity parents register it becomes a consent interruption during onboarding, which is exactly what `0022`'s header was written to avoid. Andy's call, and it wants making before launch rather than after. `E20-48` |

## `C20` · erasure beats reachability, `E20-56` / `0062`

Made 2026-08-15, after finding on production that `deactivate_recipient` failed at COMMIT for
every parent and erased nothing.

| # | Decision | Why |
|---|---|---|
| C20 | **`D10` ("guardian_link is the only path to a recipient") applies to live recipients only. An anonymised recipient is exempt** (`0062`, `assert_recipient_guardian_links`) | Erasure anonymises in place and revokes every guardian_link; the deferred `D10` constraint then refused at commit because zero links remained. Both halves were right in isolation, so one had to yield, and `D10` is a *reachability* rule — it exists so no recipient is orphaned where a guardian should be able to reach them. An anonymised row is not supposed to be reachable by anybody; it survives only so an invoice from March still resolves (`D15`). Requiring it to keep a guardian is requiring a deleted child to still belong to someone. The alternative — setting `deleted_at` instead — was rejected because `recipient_erasure.test.sql` pins `deleted_at is null` deliberately: *"an anonymised row is a live financial reference, a deleted one is a dangling key waiting to be cascaded away"*. The exemption is narrow: orphaning a live, un-anonymised child still fails, and that is asserted |
