# Decisions — Product

`P1`–`P17` · part of the decision log. Index: `docs/decisions.md`. Superseded entries and build-log history: `docs/decisions-archive.md` (never authoritative).

**Decision IDs are permanent and never move between files.** If you change a decision here, change it in the same PR as the code — never silently diverge.

| # | Decision | Why |
|---|---|---|
| P1 | School attendance is **self-declared** | Schools refused to maintain the roster. School code is dead. |
| P2 | **No holiday-calendar blocking** in v1 | Kitchen/Admin refunds to wallet instead. |
| P3 | **No per-dish capacity limits** in v1, but the counter table is designed | A `(menu_item, service_date, remaining)` row with an atomic decrement costs less than the order insert. Not a `COUNT(*)`. |
| P4 | Delivery: **bulk mark-delivered per class** + **4-digit pickup code** for counter collection + name / last-4-phone fallback | No QR printing. Pickup code goes in the confirmation email and on the invoice, so children without phones are covered. |
| P5 | Default delivery mode **parked** | Depends on real usage patterns (whole-school vs a few orders per class). Both are supported. |
| P6 | School reports = **monthly PDF emailed**, not a portal | Lands in the principal's inbox rather than waiting to be discovered. Far cheaper to build. |
| P7 | **One web app** for marketing site, admin, kitchen ops and school reports | Cheaper than three; can be split later. |
| P8 | **Read-only offline** in v1 | Offline *ordering* needs conflict handling (price change, sold out, cutoff passed) and is not worth delaying launch for. |
| P9 | **Push + email only.** No WhatsApp in v1 | Deferred, not rejected. |
| P10 | **English only** | |
| P11 | **Device tier de-emphasised.** Audience is private schools in tier-1 cities, so mid-range Androids, not bottom-tier | The real performance constraint is **network**, not CPU. Keep the menu cache, skeletons, optimistic UI, image sizing and offline reads; drop the obsession with the cheapest handsets |
| P12 | **The per-line kitchen note is built, and the packing list surfaces it.** Capped at **140 characters**; copy states it is a request passed to the kitchen on a best-effort basis, **not a guarantee and not allergy information**; retention follows the packing list (`E09-14`, option c) — fresh per service date, destroyed at end of day, nothing retained server-side | Decided by Andy 2026-08-10, settling `E09-11`. **Why it is built rather than cut:** 127 of roughly 282 non-draft legacy orders used `Dish_In_Order.special-comments` — close to half. Removing it is a visible regression from Bubble on a feature parents actually use. **Why the packing list is the condition:** the packing list is the only *per-child* artefact we produce; the production list is aggregated, so a note about one portion has nowhere to live on it. If the note does not reach the packing list it reaches nobody, and a field nobody reads is worse than no field. **Why 140 characters:** a parent writing an essay is a parent whose request will not be read in a busy kitchen at 7am. **Why the retention rule:** the moment a parent types something about their child into it, it is regulated data (§13.3), so it cannot outlive the service date it belongs to |
| P13 | **An adult may be a recipient of their own lunch, in v1.** `recipient.is_self` / `is_minor`, `guardian_relationship = 'self'`, a `self_data_notice` published alongside the child one, and `self_meal_service` / `self_allergen_info` consent purposes (`0022`). The "Myself / My child" screen is fast-follow; the model and the recipient-neutral copy are not | Decided by Andy 2026-08-10 on `docs/self-ordering-costing.md`. School staff and university students order their own lunch — 13 legacy `recipient_type = Staff` orders and a `CollegeStudent` role — and the rebuild had dropped them by omission. **The decider was the privacy notice:** published parent-only and changed later, it becomes a new policy version, and `requires_acceptance` re-prompts every existing user — landing on 150 Amity parents mid-registration as a second consent interruption during onboarding, which is the moment `AR7` can least afford one. The model change is small because `D2` already collapsed the legacy role branching into one table; the consent path gets *simpler*, because an adult consenting about themselves has no third party to verify (`[DM-12]` does not transfer) |
| P14 | **Ordering for a whole class is OUT of v1.** A teacher ordering thirty lunches at once is not built, and must not be smuggled in with `P13` | Decided by Andy 2026-08-10. Legacy `Recipient_Type` is `Child, Class, Staff`, so `Class` is real — but it is **bulk quantities and a different packing-list shape** (a count, not a list of named people), which makes it its own problem rather than a variation of ordering for one person. Recon reports no `Class` volume worth the risk. Recorded rather than left unsaid so it is not re-derived as "obviously part of self-ordering" |
| P15 | **School reporting (`E11`) is fast-follow, not v1** — recorded as a decision rather than left as an omission | It had **zero** tasks in the MVP list, so it was already excluded — but by nobody's decision, which is the dangerous kind. Andy is confirming with the schools whether a monthly report is expected at launch; if one is, we have chosen the gap and can offer something manual, rather than discovering it the week a school asks. The wider point: `docs/mvp-scope.md` is an explicit include list precisely so that exclusions are deliberate, and an epic with no ids in it defeats that unless somebody says so out loud |
| P16 | **No SMS in v1, and TRAI DLT registration is dropped.** `E00-06`–`E00-09` are out of scope, not deferred | Decided by Andy 2026-08-10. v1 is **email only** — sign-in is email OTP, order updates are email, and there is no push (non-negotiable #7). Nothing in the product sends an SMS, so a DLT Principal Entity, a `GRYBAG` header and five content templates would be weeks of approval paperwork for a channel we never use. **Recorded so it is not re-added out of caution:** the argument for starting early is that the approval chain is long, and that argument is only worth paying when there is a reason to send. If SMS is ever wanted the chain restarts from zero — that is the accepted cost, taken knowingly |
| P17 | **Six product metrics, defined in `docs/product-metrics.md`, and registered users is not one of them.** Activated users (registered **and** ≥1 paid order), weekly active orderers (distinct payers), orders per active orderer per week, AOV in paise, school penetration (% of a school's *enrolled* children with ≥1 paid order this month), cohort retention at N+4/N+8/N+12. `E10`'s dashboard renders these definitions rather than reinterpreting them | Decided by Andy 2026-08-11. **Why registered users is dropped:** Bubble reported ~400 registered against under 20 orders a week — it counts people who reached a password box, and password signup did not help it (`AR7`; passwords are gone). It stays as a *denominator* for activation and never as a headline, because promoting a denominator to a headline is exactly how ~400 came to be quoted. **Why now, before `E10`:** all six must be computable from the ledger and the order tables, and that is a property of the schema, not of the dashboard — `order_group.paid_at` set once and never cleared, one `order_group` per checkout, `"order".school_id` kept denormalised. Retrofitting them onto a schema that cannot answer them is the expensive version. **Why they cost nothing under DPDP:** money and children are already on opposite sides of the schema — orders carry who paid and which school, recipients carry who ate — so five of the six never reference a recipient at all, and the sixth counts `recipient_id` without selecting a single column of it (§2). **School penetration has no denominator yet and one is not invented:** `P1` means the only children we know are the ones parents typed in, so using that set as the denominator would report a number that *rises when adoption stalls*. It needs an enrolled-child count supplied by each school, with a provenance and an as-of date (§3, `E10-15`/`E10-16`); until then the metric reads "no enrolled count" rather than falling back to a proxy |
