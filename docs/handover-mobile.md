# Handover — mobile thread

Written for a successor with only the repository. Everything below is true as of `main` at the
time of writing; where I am uncertain I say so rather than smoothing it over.

**The one-line state: a parent can place an order, pay it with a real test-mode Razorpay payment,
and receive a compliant GST invoice by email.** That loop works end to end on staging. What is
missing is mostly recovery paths, alerting, and one accountant question.

---

## 1. Ground rules that are not obvious from the code

**Read `CLAUDE.md` first, then this.** Two rules in it were added this week and both were earned:

- **No branch runs more than a day without merging to `main`.** A three-day branch cost a false
  status report, a colliding task-id range, and two sources of truth for v1 scope.
- **Before building anything another thread might already have, check the other branch, not just
  `main`.** I read `main`, found no `mark-delivered`, and was one step from building a second one;
  it existed on `kitchen-live`. That failure recurred *within the hour* of writing the first rule.

**Ownership.** This thread owns `supabase/`, `packages/shared/` and `apps/mobile/`. The web thread
owns `apps/web/`. I edited `apps/web/src/lib/policy.test.ts` once, during a merge, and said so
loudly — that is the bar.

**`docs/learnings.md` is the highest-value file in the repo for a newcomer.** Six entries were
added this week and each one cost hours. Read it before writing a test.

## 5. Things I know that are not written down anywhere else

### The staging account trap that cost a fortnight

**`anuragdial@gmail.com` holds 17 permission grants** — every operational permission over *two*
kitchens (`GrayBag Kitchen, Mohali` and `Sky Bites`) plus platform-wide `orders.view_financials`.
All self-granted, none revoked, none expiring, and **nothing in the repo creates them**.

Consequence: **every parent-scope read performed with that account passes for the wrong reason.**
`order_read_backoffice` admits it to every order in both kitchens. `E06-43` — "My Orders" showing
65 orders, 5 of them his — was invisible for a fortnight because of exactly this.

**Use a clean parent account with zero grants** for anything parent-facing. `docs/environments.md`
§7 names `parent.tapthrough@graybag.com`; Andy's instruction on 2026-08-15 was
`anuragdial+parent@gmail.com`, which sidesteps the open question of whether `graybag.com` delivers
to that alias. Either is fine — what matters is **zero grants**. No password: v1 is email-OTP only,
so the credential is the code sent to that address.

### Authorisation is not scope

The most expensive lesson of the week, now in `learnings.md`: **a permission model is a ceiling.**
It bounds what a query *may* return and cannot express what a screen is *about*. Every table behind
a "mine" screen carries a widening policy beside the customer one (`*_read_backoffice`,
`*_read_fulfilment`, `*_read_admin`), so **RLS narrows to "mine" for no parent-facing screen.**

Scope belongs in the query; authorisation belongs in the policy; ship both. And **any test of a
scoped list must assert the count, with a third party present** — "my order appears in the list"
passes on a leak, and a two-party fixture cannot tell "scoped to me" from "scoped to one other
person".

### `safeupdate` — the trap that has bitten twice

**Hosted Supabase loads `safeupdate`; a local `supabase start` does not.** An unqualified
`DELETE`/`UPDATE` passes every pgTAP run and raises `21000` for every real request. It cost every
order (`E05-21`) and then every settlement (`E06-38`).

`scripts/check-unqualified-writes.mjs` now fails the smoke test on the pattern. **A pgTAP test
cannot guard this** — pgTAP runs where the guard is absent.

### Applying a migration by hand breaks PostgREST

If you run a migration with `psql` rather than `db push`, **PostgREST's schema cache will not see
new functions** and the RPC fails while the identical call succeeds in `psql`. Fix:
`notify pgrst, 'reload schema';`. This cost an hour with a captured payment sitting unsettled.

### Andy cannot make a UPI payment, permanently

He is in Australia. **Every payment test uses test VPAs (`success@razorpay` / `failure@razorpay`)
or a test card, in a laptop browser** — a phone with a UPI app installed launches straight into
intent and never offers the UPI-ID field. `docs/payments-design.md` §14.1 has the full split.

Two things found the hard way: **`4111 1111 1111 1111` is rejected as an international card** on a
default test account (use **netbanking**, which also has real MDR and so answers the fee question
unambiguously — UPI's zero MDR makes `fee: 0` indistinguishable from "not populated"). And the
hosted payment-link page shows a UPI QR with **no UPI-ID field** on desktop.

### Dates

Two separate traps, both of which have bitten twice:

1. **`create_checkout` asks two questions** — is the school open (`orderable_calendar`) *and* is
   the dish sold that weekday (`mi.available_days` vs `isodow`). A fixture that asks only the first
   will eventually pick a Sunday.
2. **Anything that reads the clock itself is only testable at the hour the suite runs.** IST is
   +05:30, so a UTC date is wrong for 5½ hours a day — a test against the ambient clock passes 77%
   of the time, which reads as flakiness and gets retried. `packages/shared/src/time/india.ts`
   takes the instant as an argument; do the same for anything new.

### Invoices are immutable, and three staging ones are permanently wrong

`GB/26-27/000001`–`000003` snapshot placeholder seller identity. §13.2 requires a reprint to be
byte-identical, so they **cannot** be corrected. The token guard now refuses to email them. Any new
order snapshots the real facts from `docs/legal/company.json` via
`scripts/sync-seller-identity.mjs`. **That file is the single source for entity facts** — the web
thread reads it too, and the whole point is that there is not a second copy.
