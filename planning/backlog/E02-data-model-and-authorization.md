## Why this is critical

In Bubble, `Order` is readable by everyone and 10 types have no privacy rules at all — including `Child` (minors' names, class, allergies, parent email). Authorization must be enforced server-side and covered by tests before any feature is built on top of it.

## Design decisions already locked

- Two planes: **Customer** (single ordering role) and back-office **grants** (KitchenOperator, SchoolViewer, PlatformAdmin), scoped to kitchen/school ids.
- School lives on the **Recipient**, not the user. Recipient = self or a dependent.
- `Menu` is owned by a Kitchen; `MenuAssignment(school, menu, valid_from, valid_to)` decides who sees what.
- Config **resolution chain**: platform default -> kitchen -> school. Applies to cutoff time, prices, break/drop times, revenue-share %.
- Effective config is **snapshotted onto the order** at write time (correctness + performance).
- **Ledger** (append-only credits/debits with reason codes) exists from v1 even without a visible wallet.

- [x] `E02-24` (risk:high) (mvp) **The authorization suite and `seed.sql` collide on the same UUIDs, so `npm run test:db` fails from a clean database.** `supabase/seed.sql:229` inserts `auth.users` `a0000000-0000-0000-0000-000000000001`; `supabase/tests/authorization.test.sql:147` inserts the *same* id as its own fixture, so `db reset && supabase test db` dies on `duplicate key value violates unique constraint "users_pkey"` before a single assertion runs — `Tests: 0`, not one failure but the whole suite skipped. - [x] `E02-25` (risk:critical) **CI and production do not have the same privilege baseline, so the authorization suite proves different things in each.** `docs/authorization-model.md` §10 opens by stating the model's foundation — *"Supabase's default privileges give `anon` and `authenticated` SELECT/INSERT/UPDATE/DELETE on new tables in `public`; RLS is what actually stops them."* On a real Supabase project that is true, which is why the suite went 172/172 against staging in `E02-18`. On the local CLI stack it is **not**: with `E02-24` fixed, the suite reaches its own Part 0 harness assertion at `authorization.test.sql:583` and dies on `ERROR: permission denied for table order` — `authenticated` has no privilege on the table at all, because migrations there are applied by a role whose default privileges differ. Neither environment is wrong on its own; what is wrong is that **the suite cannot mean the same thing in both**, and the one it runs in nightly is not the one that serves customers. Decide the baseline explicitly rather than inheriting it: implement §10's grants and revokes as a migration so privileges are stated in version control instead of assumed from the platform, which also closes `E02-21`. Until then a green suite locally is not evidence about production, and a red one is not necessarily a bug in the policies
- [x] `E02-26` (risk:high) **Every function in `public` was executable by `anon`, because Postgres grants EXECUTE to PUBLIC by default and nothing had ever revoked it.** Found 2026-08-09 while writing `[AUTH-01]`'s "anon may execute exactly two functions" assertion, which failed with eleven. Ten are `SECURITY INVOKER` and die on the first table they touch, but **`auth_recipient_has_fulfilment_order(uuid)` is `SECURITY DEFINER`** and therefore bypasses RLS: an unauthenticated caller holding a recipient id learns whether that **child** has a fulfilment order. Verified against the local stack — as `anon` it returns `false` rather than refusing. Not a bulk leak (recipient ids are v4 UUIDs, not enumerable), but an authorization primitive answering questions about a child to callers who have not identified themselves. Closed in migration `0010` by revoking the PUBLIC default across every non-trigger function in `public` and re-granting to `authenticated` and `service_role`. The permanent guard is the new suite assertion, which fails on the build that introduces a third anon-executable function
- [ ] `E02-27` **Make the PUBLIC-execute default impossible to reinherit.** `E02-26` revoked what existed; a function added tomorrow still arrives executable by PUBLIC and is caught only by the authorization suite. `alter default privileges in schema public revoke execute on functions from public` would stop it at the source. Left out of `0010` deliberately — default privileges apply per creating role, so getting it right needs a check of which role the CLI, CI and the hosted project each run migrations as, and that is a separate piece of work from `[AUTH-01]`
