## Approach

Sentry for errors across app/web/backend, Supabase dashboard for query performance, Better Stack for uptime. The multiplier is that **Sentry and Supabase both have MCP servers** — wired into Claude Code, a plain-English question like "orders from St. Xavier's stopped going through around 9pm yesterday, find out why" can be answered by querying errors, logs and the database directly.

- [x] `E15-15` (risk:high) **Know production is broken before a parent says so.** Andy: *"Three times this month a complete outage was invisible until a human found it by reading a log by hand — settlement failing on every attempt, every confirmation email 403ing, an entire test suite running zero files."* All three share one shape: **the system reported nothing, and nothing is what a healthy system reports.** So the rule everything here is built on is that **silence must be impossible** — every run produces a verdict and the digest is sent on a quiet day too, one line saying it was quiet. **`ops-heartbeat`**, one Edge Function, two modes. `?mode=probe` runs seven checks that **exercise rather than ping**: the marketing page must contain its own headline, `/signin` and `/kitchen` must render, two Edge Functions must answer in the shape their callers expect, a database read must return a row, and **Resend must report the `ORDER_EMAIL_FROM` domain as verified** — which is precisely the outage that 403'd every confirmation for a day (`E12-34`) and would have been caught in fifteen minutes. `?mode=digest` adds yesterday's orders, revenue, failed payments, drain depth and alerts raised, and emails it to `SUPPORT_ALERT_EMAIL`. Escalation reuses `sendMoneyAlert`, which dedupes once per kind per IST day, so a sustained outage is one email rather than ninety-six: a down endpoint, a **captured payment with no order**, a drain backlog over 20, and the digest itself failing to send. **Every probe carries a `remedy` and the type makes it awkward to add one without.** Scheduled by GitHub Actions — every 15 minutes for the probes, 07:00 IST for the digest — deliberately **outside** Supabase, because a scheduler living inside the thing it watches cannot report that the thing is down, and because `pg_cron` would have needed a migration in a week when migration numbers are held elsewhere. **No migration was written:** `ops_alert.kind` is free text by design (`0056`), so five new alert kinds were a code change. Verified end to end on staging: gateway 401 without a token, **my own 401 with a wrong secret**, seven probes green, a genuine failure escalating to a `sent` `ops_alert`, and a quiet-day digest delivered. The first version of the `policy` probe expected a GET 200 and failed against a healthy staging — the false alarm that teaches people to ignore a monitor, caught here rather than at 3am

- [x] `E15-18` (risk:high) **The PII guard for crash reporting, built before the reporter.** Andy, 2026-08-16: *"assert no child's name, class, section or allergy can reach it. That guard matters more than the reporting."* `packages/shared/src/observability/scrub.ts` removes tier P and tier S fields **by key, at any depth**, plus emails and Indian phone numbers by value. By key rather than by value because value-matching cannot work: a child called "Sweep" and a dish called "Sweet corn" are both just words, and the filter that tries to tell them apart misses real names and mangles innocent text. The structure is what we know, because our own schema chose the field names. Nine tests, and the one that matters most reads `0001_initial_schema.sql` and **fails when a `recipient` column carrying a name, class, section, allergy, phone or email is not covered** — the real failure mode is a migration adding a personal column and nobody updating the list. Also asserted: it keeps what makes a report worth having (screen, error code, HTTP status, order ref, total, dish name), survives a cycle rather than hanging (a crash reporter that hangs on a crash is worse than none), preserves an `Error`'s message and stack (spreading one loses exactly what the report is for), and bounds depth. The free-text limit is stated as a limit, not papered over: `Aarav` in a message is indistinguishable from any other word, so the defence there is that we do not put a child's name into messages
- [ ] `E15-19` (owner:andy) (risk:medium) **A Sentry DSN, and the decision about when crash reporting ships.** Blocked, and the blocker is worth stating precisely. There is **no Sentry in this repository at all** — `@sentry/react-native` is not a dependency, nothing initialises it, and `EXPO_PUBLIC_SENTRY_DSN` is read by `configure.ts` into a config nothing consumes. So this is a from-scratch build, not a wiring job, and it needs a DSN that only Andy can create. **The timing constraint is the important half**: `@sentry/react-native` is a native SDK, so adding it invalidates build 12 — currently `WAITING_FOR_REVIEW` — and requires a new binary and a new Apple review, which is the one thing the 19th cannot absorb. Two options, and it is a decision rather than a task: **(a)** ship crash reporting in the first build after launch, accepting no crash visibility for the launch window; **(b)** a JS-only reporter posting to Sentry's HTTP API, which carries no native code, ships **over the air** on top of build 12, and catches JS errors — which is most of what a JS app produces — while missing native crashes. `E15-15`'s scrubber is written and tested and is a precondition of either
- [x] `E15-17` (risk:high) **The analytics contract, as an allowlist, before any event is wired.** Andy, 2026-08-25: *"No child's identity or attributes may ever reach PostHog … A test must fail if a child field can be attached to any event, property, or person profile."* `packages/shared/src/analytics/events.ts` declares nine events and their exact properties; anything not on the list is refused. **An allowlist rather than a denylist, and the distinction is the whole design**: `observability/scrub.ts` filters a crash payload, which is whatever the runtime hands you, so stripping what you recognise is the best available move. Analytics is the opposite — we author every event, so an undeclared property is a mistake, not an unknown. A denylist fails *open* on a field nobody thought of (`nickname`, `birthday`, `class_teacher`) and the first anyone knows is a child's name in a third-party dashboard; an allowlist fails closed. 22 tests, including: every child field refused on every event; **any** person property refused, because `identify()` attaches a property to every event that identity ever sends, past and future; camelCase caught as well as snake_case, since the API layer and the components disagree about which they speak; and the `FORBIDDEN_KEYS` list checked against the real `recipient` columns in `0001`, so a migration adding a personal column cannot open a hole by nobody noticing. `child_added` deliberately carries **no** properties — it is the one event whose name invites a school, a class, a count, and each of those is an attribute of a child when the funnel question is only whether the step happened
- [x] `E15-20` **Wire the PostHog emitters — JS-only, over the air.** Blocked on Andy confirming `docs/posthog.md`, which he asked to review before emitters are built. The evaluation is done and the finding that shapes it: **`posthog-react-native` needs a native build** — it requires `expo-file-system`, `expo-application`, `expo-device` and `expo-localization`, or async-storage plus device-info, and **none of the six is currently a dependency**. So the SDK costs a binary and an App Store review. A `fetch` client against PostHog's HTTP capture endpoint ships **over the air** instead, and the features that would be lost are exactly the ones Andy is switching off — autocapture, session replay, automatic device properties. What genuinely remains is offline queueing and retry, perhaps forty lines. Residency recommendation is **Cloud EU**: DPDP s.16 restricts transfer only to notified countries and none are notified, and the payload carries no child data and no direct identifiers. Self-hosting in India is the fallback if that changes — not a licence to send more
- [x] `E15-21` **Expand the events so a parent's whole path reads in sequence.** Andy, 2026-08-26: *"so I can read a parent's whole path in sequence, not just the funnel milestones … enough that I can see someone reach checkout and turn back."* Seven new events — `screen_viewed` on every screen, plus `add_to_cart_tapped`, `remove_from_cart_tapped`, `break_time_selected`, `place_order_tapped`, `payment_sheet_closed` and `add_child_submitted` — the controls where somebody stalls or gives up. **Turning back is `payment_sheet_closed` with `outcome: dismissed` followed by the next `screen_viewed`**, and neither half is visible from the milestones alone. The change that mattered most is not an event: `screen` is the schema's first *string* property, and a screen name is exactly where a child's name would reach a vendor — `screen: "Aarav's orders"` passes a key check perfectly — so `ENUM_VALUES` now validates property **values** against a closed vocabulary, with a new `forbidden_value` rejection whose detail names the key and never the value, because a rejection is a log line and echoing it would write the child's name into the log to explain keeping it out of the vendor. Emitted from two places: one `onStateChange` listener covers the fourteen navigator routes, and `useScreenView` covers the six screens that are states rather than routes. `screens.test.ts` asserts both directions — every vocabulary entry reachable from an emitter, every route named — because a declared-but-unemitted screen reads on the dashboard as *a screen nobody visited*, which is worse than a missing row since it looks like data. Both assertions were mutation-checked rather than trusted. Session replay stays **off** and is now pinned by a test: `$snapshot` is refused, as is anything `$`-prefixed, so autocapture and replay cannot be switched on without adding a name to the allowlist. Also recorded: `cant_connect` can essentially never arrive, because the misconfiguration that renders it is the one that puts the analytics client on its no-op fallback — written into `docs/posthog.md` so a zero there is not read as "nobody hit it"

- [x] `E15-23` **A suite that ran nothing must not look like a suite that passed.** Andy: *"That belongs in CI, not in one suite."* `node --test` on a glob matching nothing exits **0** and prints `# tests 0`; `vitest --passWithNoTests` does the same — and the exit code is the only thing CI reads. That is how `authorization.test.sql` contributed zero assertions on 2026-08-08 with the pipeline green, and how `kitchen-scope.test.mjs` reported `tests 0, pass 0, fail 0` the day it was written. The integration workflow already guarded the pgTAP suite; `check:suites` generalises it to the other four and runs in the smoke test on every push. **A floor rather than "more than zero"**, because the regression that actually happens is a glob quietly matching fewer files after a rename — 181 tests becoming 12 looks perfectly healthy. Lowering a floor is then a visible diff with a reason in the commit. Proved by breaking it on purpose: with the glob renamed, `npm run test:scripts` reports `tests 0, pass 0, fail 0` and **exits 0**, while the guard exits 1 and names the suite. It also caught its own misconfiguration on the first run — `--reporter=basic` is not valid in this vitest version, so the command failed and the guard reported "could not find a test count", which is exactly what it should say when it can no longer see what it is guarding
