## Locked decisions

- **React Native + Expo**, TypeScript. Reanimated for UI-thread animation, Skia where custom motion is needed.
- **Rule:** every backend call goes through a single `api/` module. Reads use the Supabase client, **writes always go through Edge Functions**. This is what keeps "add a dedicated API server later" a config change rather than a rewrite.
- Bundle IDs are fixed and must match exactly: iOS `com.gracord.graybag`, Android `com.Gracord.Graybag` (note the capitals).

- [ ] `E14-40` (owner:andy) (risk:medium) **Maestro runs a real Android build on web-only pull requests, and adds 25–40 minutes to each.** Andy, 2026-08-28. Every web PR this week waited on an emulator boot, a Gradle build and a cart flow for a change that cannot reach the app. **The obvious fix is the dangerous one.** Putting `paths:` on the workflow means a web PR never schedules the job at all, and a required check that never reports either blocks the PR forever or — depending on how the protection rule is configured — is treated as satisfied. That is the failure `E15-23` exists about, arriving by a new route: *not run* and *passed* becoming indistinguishable. **The proposal is that the job always runs and decides inside itself.** No `paths:` on the trigger and no `if:` on the required job, so `Maestro (cart)` always reports a real conclusion. Its first step computes whether the change can affect the app; if not it writes a job summary saying so and exits successfully in about fifteen seconds. The check stays green for the right reason, and the reason is written down where a reviewer can read it. **The subtle part is what counts as mobile.** Not `apps/mobile/**` — `packages/shared` ships *inside* the app bundle, and six of the last twelve commits touched it. A filter that misses that skips the check on exactly the changes most able to break the app silently. The list has to be `apps/mobile/**`, `packages/shared/**`, `.maestro/**` and the workflow itself, with a test asserting the list rather than a comment describing it. **And the backstop is what makes it safe**: Maestro runs unconditionally on push to `main` and in the nightly. If the filter is ever wrong, the cost is finding out within a day rather than never — which is a different and acceptable risk, and is the part that answers "a check that does not run looks like one that passed"
- [x] `E14-41` **The scripts suite runs serially, because the meal-pack tests are not isolated from it.** Adding one unrelated test file — `check-build-order.test.mjs`, which reads two files from disk and touches no database — turned `meal-pack-concurrency` and `pack-eligibility-agreement` red. **Nondeterministically**: four failures on one run, two on the next, zero in isolation, zero twice in isolation. `node --test` runs files concurrently up to the core count, so adding a file changes what runs beside what, and those tests contend with the rest of the suite over shared database state. **The trigger is arbitrary and that is the point** — the next person to add any test file would have hit it, and would have spent an hour proving their own change innocent, as this did. `--test-concurrency=1` makes it deterministic and costs **nothing measurable**: 196 tests in 7.7 seconds.
