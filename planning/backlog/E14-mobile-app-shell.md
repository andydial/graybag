## Locked decisions

- **React Native + Expo**, TypeScript. Reanimated for UI-thread animation, Skia where custom motion is needed.
- **Rule:** every backend call goes through a single `api/` module. Reads use the Supabase client, **writes always go through Edge Functions**. This is what keeps "add a dedicated API server later" a config change rather than a rewrite.
- Bundle IDs are fixed and must match exactly: iOS `com.gracord.graybag`, Android `com.Gracord.Graybag` (note the capitals).

- [x] `E14-36` (risk:high) **The `Maestro (cart)` CI job timed out at 45 minutes on every pull request, and had never once passed.** Not slow — the Gradle daemon exhausted its metaspace and then neither finished nor died, throwing `OutOfMemoryError: Metaspace` in a loop until the job's own timeout killed it. Expo's template ships `-Xmx2048m -XX:MaxMetaspaceSize=512m` (verified by running `prebuild` with the plugin removed, not read from docs); metaspace holds class metadata and is a separate region, so the usual "raise `-Xmx`" advice would have changed nothing. Fixed as a config plugin rather than a CI line because `android/` is generated by `prebuild` and not committed, so a `gradle.properties` edit is erased every build — and because EAS runs the same Gradle, and the two must not disagree. `ExitOnOutOfMemoryError` is the half that bounds the damage: the same exhaustion now kills the JVM in minutes with the reason in the log. 7 assertions. **Second half, found by fixing the first:** with the APK building (24m34s), the job still hit 45 minutes — the emulator took **781 seconds to boot** because `/dev/kvm` is not world-writable on a GitHub runner, so it silently fell back to software emulation. The job's total work had always exceeded its own timeout, so the OOM fix only moved the wall. A udev rule, an AVD snapshot cache and a 75-minute ceiling
- [x] `E14-37` (risk:high) **`Maximum update depth exceeded` on the waiting screen, during the first real payment.** The poller updated an `elapsedMs` state every two seconds and its effect depended on the object `useCheckout()` returns — which is rebuilt every render, so each tick re-subscribed the effect. **It starved the poll it existed to drive**: the payment captured at Razorpay and the order never settled. Fixed by taking the clock out of render state entirely — the screen needs one threshold crossing (§5.12's ten seconds), so that is one boolean set by one `setTimeout` instead of a state write per tick — and by depending only on primitives and stable callbacks
