## Why this is the riskiest epic

Real money, live users, and the legacy implementation has a public webhook endpoint (`payment_processed`) with no visible server-side signature verification. Stripe is being dropped entirely; Razorpay only.

The de-risking spike now lives in **`E19-01`** and runs in phase 1, long before this epic starts. Do not begin E06 design until it has an answer.

- [x] `E06-03` (risk:critical) (mvp) **Signature verification**, both signatures. `supabase/functions/_shared/signature.ts`: the webhook HMAC over the **raw body** (§5.2 — parsing and re-serialising changes key order, whitespace and escaping, so the HMAC never matches and the failure is total, uniform and indistinguishable from an attack), and the callback HMAC over `order_id|payment_id` with the **key** secret, the shape `E19-01` confirmed on a handset. Constant-time hex comparison. Fails **closed** on a missing secret or header. Pure Web Crypto and no Deno globals, so it is imported by the Edge Function and by a vitest suite — the one piece of cryptography in the product is not the one piece with no tests. 17 assertions including an RFC 4231 vector, so the test cannot agree with a broken implementation
- [x] `E06-04` (risk:critical) (mvp) **The webhook endpoint** — `supabase/functions/payments-webhook`. Raw bytes first, HMAC, then `JSON.parse` **only after verifying**, then insert `on conflict do nothing` (§7.1 layer 4). **Always `200`**, including on a bad signature — a `4xx` makes Razorpay retry a request we will never accept and the storm buries the real events. The single exception is a failed INSERT: the event is then recorded nowhere and their retry is the only remaining copy, so that alone returns `500`. **Records; does not settle** — `settle_payment` (`E06-06`) runs from the recorded row, so an event storm cannot become a settlement storm. Unverified events are recorded `ignored` and never picked up

- [x] `E06-06` (risk:high) (mvp) **`settle_payment` — a verified capture becomes a confirmed order.** `0046`. Payment to `captured`, orders to `paid` via T5 as `system`, a §9.4 four-digit pickup code per order allocated **on capture** (`OrderPlacedScreen` refuses to render without one, treating its absence as a second witness that money did not move), the sale posted to the ledger across revenue and the two tax accounts, `paid_at` stamped, all under the group lock. **Idempotent without a flag**: §7.1 layers 5-8 refuse every write of a repeat, so the test replays the whole function rather than checking a boolean — a duplicate delivery returns the same pickup code and does not double the money. Refuses an amount that is not what the customer was shown (`L7`) and a provider order we have no record of (§10.9, almost always the other environment). Does **not** decide that money moved (`R8`/§3.6): the caller fetches the payment from Razorpay and passes what the provider says. 14 assertions. Failure handling, the sweeper and the app-kill path remain — `E06-16`/`E06-17`
- [x] `E06-07` (risk:critical) (mvp) **Ledger — the one way in.** `0038`. The guarantees already existed (`0001`'s append-only and deferred zero-sum triggers, `0013`'s structural sign convention, `0035`'s accounts); what was missing was a posting API, without which every caller assembles a transaction by hand and the zero-sum trigger is the only thing that notices — at COMMIT, with the statement long gone. `post_ledger_transaction()` refuses fewer than two entries, a non-positive amount (**direction carries the sign and is the only thing that does — a negative credit balances**), an unbalanced posting, an unknown or deactivated account, and a reason code that is not `category = 'ledger'` (the foreign key alone accepts `customer_request`). Accounts are named by **code**, never uuid. Optional idempotency key: a repeat returns the existing transaction and writes nothing, and a repeat with *different* amounts still returns the first — a retry must never rewrite an append-only ledger. `reverse_ledger_transaction()` is the only correction: an equal and opposite posting linked by `reversal_of_transaction_id`, keeping the original reason code and stamping `occurred_at` with now. 19 pgTAP assertions, most of them about what it refuses
